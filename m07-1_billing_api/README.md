# m07-1 · Billing API

Сервис списания кредитов для генерации AI-видео. Пользователь создаёт задание на генерацию: стоимость списывается с его кошелька, задание записывается в базу, и всё это происходит в одной транзакции. Если кредитов не хватает, задание не создаётся.

FastAPI + PostgreSQL + Docker. Логика списания взята из задачи [m06-2_billing](../m06-2_billing).

**Демо:** <ССЫЛКА_НА_RENDER>/docs

Сервис на бесплатном тарифе Render: после простоя первый запрос может идти до минуты, пока сервис просыпается.

## Эндпоинты

| Метод | Путь | Ключ | Что делает |
|---|---|---|---|
| `POST` | `/jobs` | нужен | создаёт задание и списывает `cost` с кошелька |
| `GET` | `/jobs/{id}` | — | задание по id |
| `GET` | `/wallets/{user_id}` | — | кошелёк пользователя и баланс |
| `GET` | `/health` | — | проверка, что сервис жив |

`POST /jobs` закрыт ключом: его нужно передать в заголовке `X-API-Key`.

Тело запроса:

```json
{"user_id": 1, "prompt": "неоновый город ночью", "model": "fast", "cost": 10}
```

Ответы:

| Код | Когда |
|---|---|
| `200` | задание создано, в ответе `job_id` |
| `401` | нет ключа или ключ неверный |
| `402` | на балансе меньше `cost` |
| `404` | пользователя нет |
| `422` | тело не прошло валидацию: `model` не `fast`/`pro`, промпт короче 5 символов, `cost` ≤ 0 |

## Как устроено списание

1. `SELECT ... FOR UPDATE` блокирует строку кошелька. Два одновременных запроса одного пользователя выполняются по очереди, а не оба читают старый баланс.
2. Проверяется баланс.
3. `UPDATE wallets` списывает кредиты, `INSERT INTO jobs ... RETURNING id` создаёт задание.
4. Всё это одна транзакция: если любой шаг падает, не применяется ничего.

## Как запустить локально

Нужен Docker.

```bash
git clone https://github.com/OralbekovAbzal/ai_prep.git
cd ai_prep/m07-1_billing_api
cp .env.example .env        # заполнить KEY и POSTGRES_PASSWORD
docker compose up --build
```

Документация откроется на http://localhost:8000/docs.

При первом запуске Postgres выполнит `init.sql`: создаст таблицы и тестовые данные (5 пользователей, 50 заданий). Данные хранятся в volume `pgdata` и не пропадают после `docker compose down`. Сбросить базу до исходных данных: `docker compose down -v`.

Переменные окружения:

| Переменная | Зачем |
|---|---|
| `KEY` | ключ для `POST /jobs` |
| `POSTGRES_PASSWORD` | пароль Postgres в контейнере `db` |
| `DATABASE_URL` | адрес базы. В compose задаётся автоматически и указывает на сервис `db` |

Проверка:

```bash
curl -X POST localhost:8000/jobs \
  -H "X-API-Key: <твой KEY>" \
  -H "Content-Type: application/json" \
  -d '{"user_id": 1, "prompt": "неоновый город ночью", "model": "fast", "cost": 10}'

curl localhost:8000/wallets/1     # баланс уменьшился на 10
```

В тестовых данных у пользователя 5 (Abzal) баланс 0, так что на нём удобно проверять ответ 402.

## Деплой

Сервис задеплоен на Render:

- **Веб-сервис** собирается из `Dockerfile` в репозитории при каждом пуше. `docker-compose.yml` на Render не используется, он только для локального запуска.
- **База** — управляемый PostgreSQL на Render. Схема и данные залиты один раз из `init.sql` по внешнему адресу базы:
  ```bash
  docker run --rm -i postgres:16 psql "<External Database URL>" < init.sql
  ```
- **Переменные окружения** заданы в настройках сервиса на Render: `DATABASE_URL` (внутренний адрес базы) и `KEY`. Файл `.env` в репозиторий не попадает.
