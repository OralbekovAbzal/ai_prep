# m11-1 · Поиск по смыслу

Семантический поиск по описаниям движений камеры и приёмов съёмки в Postgres с pgvector. Запрос «камера кружится вокруг здания» находит `orbit`, хотя общих слов с описанием почти нет.

Эти 30 описаний станут базой знаний для агента в итоговом проекте «Раскадровщик»: он будет искать по ним подходящее движение камеры для каждого кадра.

## Как устроено

1. **Данные.** 30 описаний движений камеры и приёмов съёмки на русском: dolly, orbit, crane, rack focus, dutch angle, time-lapse и другие, по 2–3 предложения. В описаниях специально прописаны различия у пар, которые легко спутать: `dolly_in` и `zoom_in`, `pan` и `truck`, `crane_up` и `pedestal`.
2. **Эмбеддинги.** Каждое описание превращается в вектор из 768 чисел моделью `gemini-embedding-2`:
   - `output_dimensionality=768` — в 4 раза легче вектора по умолчанию, почти без потери качества. Индекс HNSW в pgvector работает с векторами до 2000 измерений;
   - `task_type`: описания кодируются как `RETRIEVAL_DOCUMENT`, запросы — как `RETRIEVAL_QUERY`. Короткий вопрос и длинное описание выглядят по-разному, и модель строит векторы так, чтобы вопрос оказался рядом с подходящим описанием.
3. **Хранение.** Postgres с расширением pgvector: название, текст описания и вектор.
4. **Поиск.** Запрос превращается в вектор той же моделью и той же размерности, затем база сортирует описания по косинусному расстоянию (`<=>`) и возвращает 3 ближайших.

## Схема

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE camera_moves (
    id bigserial PRIMARY KEY,
    name text NOT NULL,
    description text NOT NULL,
    embedding vector(768) NOT NULL
);

CREATE INDEX ON camera_moves USING hnsw (embedding vector_cosine_ops);
```

Способ расстояния в индексе (`vector_cosine_ops`) совпадает с оператором в запросе (`<=>`), иначе Postgres индекс не использует.

## Проверка: 10 запросов

Запросы написаны своими словами, а не фразами из описаний. Для каждого записано место правильного ответа в выдаче, а по ним посчитаны три метрики:

- **Hit rate @1** — доля запросов, где правильный ответ на первом месте;
- **Hit rate @3** — доля запросов, где правильный ответ вообще попал в топ-3;
- **MRR** (Mean Reciprocal Rank) — среднее от 1 / место правильного ответа (0, если не найден). Показывает, насколько высоко в среднем стоит правильный ответ.

| Метрика | Результат |
|---|---|
| Hit rate @1 | **90%** |
| Hit rate @3 | **100%** |
| MRR | **0,93** |

| Запрос | Ожидалось | Топ-3 |
|---|---|---|
| камера кружится вокруг здания | orbit | **orbit**, camera_roll, crane_up |
| снимаем сверху тарелку с едой на столе | top_down | **top_down**, handheld, static |
| все замирает, но капли воды медленно движутся | slow_motion | **slow_motion**, static, time_lapse |
| камера приближается к лицу, но фон не смещается | zoom_in | **zoom_in**, dolly_in, crash_zoom |
| камера движется вместе с машиной | truck | **truck**, tracking_shot, handheld |
| в начале виден один дом, затем камера поднимается вверх и виден весь город | drone_reveal | crane_down, crane_up, **drone_reveal** |
| изображение слегка трясётся, как будто снимают на телефон в толпе | handheld | **handheld**, whip_pan, static |

## Что видно из результатов

- **Похожие пары различаются правильно.** `zoom_in` стоит выше `dolly_in`, `truck` — выше `tracking_shot`. Различия, прописанные в описаниях, модель уловила.
- **Вторые места осмысленные.** После `zoom_in` идёт `dolly_in`, после `truck` — `tracking_shot`, после `low_angle` — `crane_down`. Эмбеддинги понимают, какие движения похожи.
- **Эмбеддинги плохо различают направление.** В единственной ошибке на первом месте оказался `crane_down` (камера опускается), хотя в запросе камера поднимается. Тема совпадает (кран, высота, город), а «вверх» и «вниз» для векторов почти одно и то же. Такое же бывает с отрицаниями («есть» и «нет»). Это аргумент дополнить векторный поиск полнотекстовым (задача m11-3).
- **Эталон в этом запросе спорный.** В запросе нет слова «дрон», и «камера поднимается, виден весь город» подходит и для `crane_up`. Человек тоже засомневался бы между ними.
- **Некоторые описания всплывают везде.** `camera_roll` и `static` попадают в топ-3 к несвязанным запросам: их описания оказались «средними» по смыслу. На 30 записях это не мешает, на тысячах документов такие записи засоряют выдачу.

## Ограничения

- **Набор маленький и немного подогнанный.** Часть запросов написана тем же автором, что и описания, поэтому формулировки близки. Для честной оценки нужны запросы от других людей, короткие («облёт»), на английском («orbit shot») и разговорные.
- **Индекс на 30 строках почти бесполезен.** Postgres может решить, что быстрее перебрать таблицу целиком. Проверяется через `EXPLAIN`. Индекс создан на будущее, для больших объёмов.
- **Повторный запуск заливки создаёт дубли:** на `name` нет ограничения `UNIQUE`.

## Как запустить

Нужен Postgres с pgvector. Проще всего в Docker:

```bash
docker run -d --name pgvector \
  -e POSTGRES_PASSWORD=<пароль> -e POSTGRES_DB=rag \
  -p 5433:5432 pgvector/pgvector:pg16
```

Порт 5433 на маке, чтобы не конфликтовать с другим Postgres на 5432.

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install google-genai "psycopg[binary]" python-dotenv
```

Файл `.env`:

```
GEMINI_API_KEY=ключ из Google AI Studio
DATABASE_URL=postgresql://postgres:<пароль>@localhost:5433/rag
```

Создать таблицу и индекс (SQL выше), затем:

```bash
python embeddings.py   # считает эмбеддинги 30 описаний и сохраняет в базу, запускать один раз
python main.py         # прогоняет 10 запросов и печатает hit rate @1, @3 и MRR
```
